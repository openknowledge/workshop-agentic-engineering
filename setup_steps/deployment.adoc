= Deployment

Um das Projekt zu deployen, verwenden wir dokploy, ein Tool, das speziell für die Bereitstellung von Docker-Anwendungen entwickelt wurde. Es ermöglicht es uns, unsere Anwendung einfach und schnell auf verschiedenen Plattformen zu deployen, ohne uns um die Details der Infrastruktur kümmern zu müssen. Dokploy bietet ein Layer (UI als auch API) on-top-of Docker Swarm, um Applikationen, welche in einer docker-compose definiert sind, zu deployen. Es bietet außerdem die Möglichkeit, verschiedene Stages (z.B. Development, Test, Integration, Production) zu verwalten und zu deployen.

Um Anwendungen zu deployen, müssen zunächst einige Schritte manuell in dokploy (https://dokploy.apps.openknowledge.services) vorgenommen werden.

== Initiales Deployment in dokploy

=== Development Environment einrichten

1. Erstelle ein neues Projekt in dokploy und verbinde es mit deinem Git-Repository.
2. Erstelle ein neues Environment "develop".
3. Erstelle einen neuen Service "Compose" und nenne ihn "compose".
4. Klicke auf "compose".
5. Wähle Git als Source und trage folgende Einstellungen ein:
    - Repository URL: Dein Git Repository
    - Branch: `develop`
    - Compose Path: `deployment/docker-compose.yaml`
    - SSH-Key: Wähle einen vorhandenen SSH-Key oder erstelle einen neuen. Der SSH-Key muss in deinem Git-Repository hinterlegt sein, damit dokploy Zugriff auf den Code hat.
6. Setze folgende Umgebungsvariablen unter dem Tab "Environment":
    - `APP_PG_PASSWORD`: Das Passwort für die PostgreSQL Datenbank (z.B. ein starkes Passwort)
    - `APP_IMAGE_TAG`: Der Docker Image Tag (muss mit `dev` übereinstimmen, da die CI Pipeline den Tag `dev` setzt)
7. Klicke auf "Deploy" und warte, bis der Deploy-Prozess abgeschlossen ist.
8. Klicke danach auf "Domains" und anschließend auf "Add Domain". Hinweis: Alle Subdomains von "apps.openknowledge.services" zeigen bereits auf den Server. Als Konvention für die URL gilt: `<environment-name>.<project-name>.apps.openknowledge.services`
9. Gib folgende Einstellungen für die Domain ein:
    - Service Port: Wähle den `auth-proxy` Service oder `<service-name>`, abhängig davon, ob du Basic Auth haben möchtest
    - Host: `develop.<project-name>.apps.openknowledge.services` (z.B. `develop.basisprojekt.apps.openknowledge.services`)
    - Container Port: `80` (für auth-proxy) oder `8080` (für z. B. basisprojekt-server)
    - HTTPS: Enabled
    - Certificate Provider: Let's Encrypt
10. Klicke auf "Add Domain". Anschließend musst du nochmal im Tab "General" auf "Deploy" klicken, damit die Domain eingerichtet wird. Warte, bis der Deploy-Prozess abgeschlossen ist.
11. Sobald die Domain eingerichtet ist, kannst du deine Anwendung über die URL `develop.<project-name>.apps.openknowledge.services` erreichen.

=== Production Environment einrichten

Wiederhole den obigen Vorgang für Production mit folgenden Unterschieden:

1. Erstelle ein neues Environment "production"
2. Erstelle einen neuen Service "Compose" und nenne ihn "compose-production"
3. Branch: `main` (statt `develop`)
4. `APP_IMAGE_TAG`: `latest` (da die CI Pipeline den Tag `latest` für main pusht)
5. Domain: `prod.<project-name>.apps.openknowledge.services` oder eine ähnliche Konvention

== Deployment neuer Versionen

Das Deployment ist automatisiert über die CI Pipeline:

1. **Push zu `develop` Branch**: Die CI Pipeline baut das Projekt, erstellt ein Docker-Image mit dem Tag `dev` und pushes es in die Registry. Die `deploy` Job triggert dann automatisch ein Redeployment des `compose` Services in dokploy.

2. **Push zu `main` Branch**: Ähnlich wie bei `develop`, aber mit dem Tag `latest` für Production. Die CI Pipeline triggert automatisch ein Redeployment des `compose-production` Services in dokploy.

Die automatische Deployment-Auslösung erfolgt via Dokploy API (siehe `deploy` Job in `.gitlab-ci.yml`).

== Automatisierung des Deployments mit GitLab CI

Um das automatische Deployment via GitLab CI zu aktivieren, müssen folgende Variablen in den GitLab-CI/CD Settings hinterlegt werden:

- `DOKPLOY_DEPLOYMENT_KEY`: Der API-Key, welcher in dokploy unter Settings > API Keys generiert werden kann. Er wird benötigt, damit die GitLab-CI/CD Pipeline Zugriff auf die Dokploy API hat.
- `DOKPLOY_DEV_COMPOSE_ID`: Die ID des `compose` Services in der `develop` Environment in dokploy. Diese ID findest du in der Dokploy UI unter dem Service in der URL oder in den Service-Details. Sie wird benötigt, damit die GitLab-CI/CD Pipeline weiß, welchen Service sie für Development deployen soll.
- `DOKPLOY_PRODUCTION_COMPOSE_ID`: Die ID des `compose-production` Services in der `production` Environment in dokploy. Analog zu `DOKPLOY_DEV_COMPOSE_ID`.

Weitere Details siehe link:ci-pipeline.adoc[CI Pipeline].

== Docker Compose Files

Das Deployment ist mit Docker Compose Files umgesetzt. Es gibt in dem Projekt insgesamt zwei Docker Compose Files:

- `docker-compose.yaml` (Projekt-Root): Wird für das lokale Starten der Anwendung während der Entwicklung verwendet. Es definiert die Services für die lokale Entwicklung (z.B. Server, Datenbank, Flyway Migrations, OpenTelemetry Collector). Der Datenbank Server und die Flyway Migration können auch separat gestartet werden, und die Applikationen können jeweils lokal über die IDE gestartet werden, um z.B. die Debugging-Möglichkeiten zu nutzen. Siehe link:dev_setup.adoc[Dev Setup].

- `deployment/docker-compose.yaml`: Wird für das Deployment in dokploy verwendet. Es definiert die Production-Services (z.B. Server, Datenbank, Flyway Migrations, OpenTelemetry Collector). Zusätzlich enthält es:
  - **Basic Auth Proxy** (nginx): Alle Deployments sind standardmäßig mit Basic Auth geschützt. Das nginx Proxy-Service lädt die htpasswd-Datei mit Authentifizierungsdaten. Der aktuelle Standard-Benutzer ist `okuser`.
  - **Environment-Variablen**: Der Service nutzt `APP_PG_PASSWORD` und `APP_IMAGE_TAG` Umgebungsvariablen, welche in dokploy konfiguriert werden müssen.
  - **Testdaten**: Das lokale `docker-compose.yaml` lädt Testdaten in die Datenbank (via Flyway testdata), aber nicht in der `deployment/docker-compose.yaml`. Dies ermöglicht es, die Staging- und Production-Umgebungen mit echten Daten zu starten.

Hinweis: Es gibt kein separates `production-docker-compose.yaml`. Stattdessen wird die gleiche `deployment/docker-compose.yaml` für beide (Staging/Dev und Production) verwendet, unterscheidet sich aber durch die Umgebungsvariablen (`APP_IMAGE_TAG`: `dev` vs. `latest`).
