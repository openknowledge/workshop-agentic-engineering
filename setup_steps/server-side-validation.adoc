= Serverseitige Validierung

Die serverseitige Validierung erfüllt zwei Ziele.
Erstens wollen wir bei Benutzereingaben sicherstellen, dass sie valide sind.
Valide beinhaltet dabei nicht nur die fachliche Korrektheit,
sondern auch die Einhaltung technischer Grenzen wie die Größen von Datenbankspalten.
Für den Nutzerkomfort wollen wir diese Fehler
außerdem sprechend an den Client kommunizieren.
Wichtig ist, dass die Validierung von Nutzereingaben
nicht nur dem Komfort des Benutzers dient, sondern auch ein Sicherheitsfeature ist.
Überläufe und Injections können so verhindert werden.

Das zweite Ziel ist die möglichst frühe Erkennung von Programmierfehlern.
Um langfristig robuste und wartbare Systeme zu entwickeln, ist es essenziell,
dass Programmier- und Modellierungsfehler zum frühestmöglichen Zeitpunkt erkannt werden.

Zusammengesetzte Records (z.B. `Customer`) bestehen nur aus anderen Records.
Jeder dieser Records validiert sich selbst.
Damit Bean Validation in die verschachtelten Records hineinwirkt,
müssen die Komponenten mit `@Valid` annotiert werden.

=== Kein Validieren im Konstruktor

Der (kanonische) Konstruktor eines Records enthält *keine* Validierung.
Der Grund ist, dass Records von Jackson (JSON), Hibernate (JPA) und Spring (Request-Parameter)
über den Konstruktor erzeugt werden und die Validierung bei diesen Wegen immer nachträglich
per Bean Validation erfolgt (z.B. durch `@Valid` am Controller-Parameter).
Eine Validierung im Konstruktor würde dort die gesammelten, strukturierten Fehlermeldungen verhindern,
weil schon der erste Fehler beim Erzeugen als Exception auftritt.

Im Konstruktor ist lediglich eine *Normalisierung* erlaubt,
z.B. das Entfernen von Leerzeichen mit `trim()`:

[source,java]
----
public record LastName(@JsonValue @NotBlank @Size(max = MAX_LENGTH) String lastName) {

    public LastName {
        lastName = lastName != null ? lastName.trim() : null;
    }
}
----

Weil die Validierung erst nach dem Konstruktor stattfindet,
muss man im Konstruktor immer damit rechnen,
dass die Parameter invalide sind, z.B. `null`.
Der Konstruktor muss deshalb null-sicher sein und darf nicht selbst an ungültigen Werten scheitern.

=== Factory-Methoden für Code-erzeugte Objekte

Objekte, die im Code (und nicht durch das Framework) erzeugt werden,
werden über eine statische Factory-Methode `new<RecordName>` erzeugt.
Diese ruft den Konstruktor auf und validiert das Ergebnis sofort programmatisch über `Validate.validate(...)`.
Bei Fehlern wird eine `IllegalArgumentException` geworfen,
deren Stacktrace auf die Stelle verweist, die das ungültige Objekt erzeugen wollte:

[source,java]
----
public static CustomerId newCustomerId(Long customerId) {
    return validate(new CustomerId(customerId));
}
----

Den kanonischen Konstruktor ruft deshalb außer der Factory-Methode niemand direkt auf.
Die einzige Ausnahme sind Konvertierungs-Konstruktoren mit einem `String`-Parameter (siehe oben),
die vom Framework verwendet werden und deren Ergebnis danach per `@Valid` validiert wird.

=== Absicherung durch Architekturtests

Diese Regeln werden im `ValueObjectTest` (ArchUnit) automatisch geprüft:

* Controller sind mit `@Validated` annotiert, ihre Record-Parameter mit `@Valid`,
  und sie verwenden keine einfachen Typen als Parameter.
* Record-Komponenten, die selbst Records sind, sind mit `@Valid` annotiert.
* Records mit einer einzelnen Komponente haben eine Bean-Validation-Constraint (außer bei `boolean`).
* Zusammengesetzte Records bestehen nur aus anderen Records.
* Der kanonische Konstruktor ist null-sicher.
* Der kanonische Konstruktor wird nur von der Factory-Methode `new<RecordName>` (oder einem `String`-Konstruktor) aufgerufen.
* Die Factory-Methode gibt genau das Objekt zurück, das sie validiert hat.

=== Entitäten

In Entitäten und Aggregates muss sichergestellt werden,
dass auch in den Update-Methoden keine fehlenden Werte gesetzt werden.
Die übergebenen Records sind dabei bereits validiert,
da sie entweder über die Factory-Methode oder durch `@Valid` am Controller entstanden sind.
