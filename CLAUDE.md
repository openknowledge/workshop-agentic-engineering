# Basisprojekt

Base project template by open knowledge GmbH for starting new projects with a standard Java/React tech stack.

## Tech Stack

- **Backend:** Java 21, Spring Boot 3.5.7, Spring Data JPA (EntityManager), PostgreSQL 17
- **Frontend:** React 19.1, TypeScript 5.9, Vite 7.1
- **Build:** Maven multi-module (`pom.xml` at root), frontend-maven-plugin (Node v24.10.0)
- **Database:** PostgreSQL 17, Flyway migrations, Testcontainers for tests
- **Formatting:** Spotless (Google Java Format AOSP style) + Checkstyle (OK Coding Conventions) for Java; Prettier + ESLint for TypeScript/React
- **Testing:** JUnit 5, Spring Boot Test, Testcontainers, AssertJ, RestClient
- **CI/CD:** GitLab CI (`.gitlab-ci.yml`)
- **Container:** Multi-stage Dockerfile, docker-compose
- **License:** Apache 2.0

## Architecture

Multi-module Maven project with feature-based package structure.

- `basisprojekt-server/` -- Spring Boot backend (REST API, JPA, Flyway)
  - `src/main/java/de/openknowledge/baseproject/` -- Application root package
    - `<feature>/domain/` -- Domain logic: entities, records, repositories, services
    - `<feature>/web/` -- REST controllers
  - `src/main/resources/db/migration/` -- Flyway SQL migrations
  - `src/main/checkstyle/` -- Checkstyle configuration files
  - `src/test/` -- Integration tests with Testcontainers
- `basisprojekt-client/` -- React/TypeScript frontend (Vite, TanStack Router/Query/Table/Form, Zod)
  - `src/components/` -- Shared reusable components (FormField, etc.)
  - `src/features/<feature>/api/` -- API functions + TanStack Query hooks
  - `src/features/<feature>/components/` -- Feature-specific components (forms, tables)
  - `src/features/<feature>/schemas/` -- Zod schemas + TypeScript types
  - `src/routes/` -- TanStack Router file-based routes
- `architecture-decision-records/` -- ADRs in AsciiDoc format
- `setup_steps/` -- Project setup documentation in AsciiDoc

## Coding Guidelines

### Java Naming Conventions

- Packages: all lowercase, dot-separated (`de.openknowledge.baseproject.counter.domain`)
- Classes/Types: PascalCase, each word capitalized (`CounterEntity`, `CounterService`)
- Methods/Variables: camelCase (`findCounter`, `counterService`)
- Constants: UPPER_SNAKE_CASE (`BY_NAME`)
- DB tables: `TAB_` prefix, uppercase (`TAB_COUNTER`)
- DB columns: `C_` prefix, uppercase (`C_ID`, `C_NAME`, `C_VALUE`)
- DB sequences: `SEQ_` prefix (`SEQ_C_ID`)
- Flyway migrations: `V<major>.<minor>.<patch>__<description>.sql` (`V1.0.0__create-counter.sql`)

### TypeScript/React Naming Conventions

- Files: PascalCase for components (`App.tsx`), camelCase for utilities and API files (`customerApi.ts`)
- Components: PascalCase function components (`function App()`)
- Variables/functions: camelCase
- CSS files: match component name (`App.css`)
- Schemas: camelCase (`customerSchema.ts`), one file per feature

### Frontend Patterns

- **Schemas:** ONE Zod schema per feature, used both for form validation and as the API resource type; add `.catchall(z.unknown())` if the resource carries fields the form doesn't edit, so they round-trip without a second parallel type
- **Form fields:** Use the shared `FormField` component (`src/components/FormField.tsx`); do NOT inline form field markup
- **Form errors:** TanStack Form + Zod (Standard Schema) returns error objects, not strings -- extract `.message` from each error
- **Routing:** TanStack Router file-based routing; route tree auto-generated by Vite plugin; never edit `routeTree.gen.ts`
- **API layer:** Separate `<feature>Api.ts` (fetch calls) from `<feature>Queries.ts` (TanStack Query hooks)
- **Sanitize form data:** Convert empty strings to `null` for optional fields before sending to API

### Code Structure & Patterns

- **Feature-based packages:** Group by feature (`counter/`), then by layer (`domain/`, `web/`)
- **Domain objects as Java records:** Use `@Embeddable` records for value objects (`Counter`, `CounterName`, `CounterValue`)
- **Entities:** Separate entity class wrapping domain record via `@Embedded` (`CounterEntity` wraps `Counter`)
- **Repositories:** Use `EntityManager` with `@PersistenceContext` and `@NamedQuery` -- not Spring Data JPA interfaces
- **Services:** `@Service` + `@Transactional`, use `@Autowired` field injection
- **Controllers:** `@RestController` + `@RequestMapping`, use `@Autowired` field injection
- **JSON serialization:** Use `@JsonValue` on record components for automatic serialization
- **Static imports:** Import static members explicitly (e.g., `import static jakarta.persistence.GenerationType.SEQUENCE`)
- **Import order:** Static imports first, then regular imports, no star imports, unused imports removed (enforced by Spotless)
- **Java line length:** Max 140 characters
- **Java indentation:** 4 spaces, no tabs
- **Line endings:** LF (Unix-style)

### Error Handling

- Use `ResponseStatusException` with HTTP status codes in controllers for API errors
- Use `Optional` return types for queries that may return no result
- Use `Objects.requireNonNull()` for constructor parameter validation in entities
- Do NOT use `System.out`, `System.err`, or `.printStackTrace()` -- use a logger instead (checkstyle enforced)

### Database Patterns

- Flyway for schema migrations in `src/main/resources/db/migration/`
- Table naming: `TAB_<ENTITY>`, column naming: `C_<FIELD>`
- Sequences: `SEQ_<COLUMN>` with `allocationSize = 1`
- Entity ID: `@GeneratedValue(strategy = SEQUENCE)` with explicit `@SequenceGenerator`
- Named queries defined on entity class with `@NamedQuery`
- Constraints: `pk_` prefix for primary keys, `uq_` prefix for unique constraints

### Testing Rules

- Integration tests with `@SpringBootTest(webEnvironment = RANDOM_PORT)`
- Testcontainers for PostgreSQL (`@Container @ServiceConnection`)
- Flyway enabled via `properties = "spring.flyway.enabled=true"`
- Test data in `src/test/resources/db/testdata.sql`
- Use AssertJ (`assertThat`) for assertions, JUnit `assertTrue` for simple checks
- Test with `RestClient` for HTTP calls, pattern: Given/When/Then comments
- Test class name: `<Feature>Test` (e.g., `CounterControllerTest`)

## Development Workflow

When implementing any feature, bugfix, or non-trivial change, Claude MUST follow this mandatory sequence:

### Step 1: Architect First

Before writing ANY implementation code, launch the **architect** agent to analyze the codebase and produce an implementation plan. The architect will:
- Analyze existing patterns and decide which files to create/modify
- Define class structures, database migrations, and REST endpoints
- Write the plan to a markdown file

Do NOT skip this step. Do NOT start coding without an architect plan.

### Step 2: Implement Following Code Patterns

After the architect plan is approved, load the **code-patterns** skill (`references/implementation-examples.md`) and follow its templates exactly when writing code. Every new file MUST match the existing patterns:
- Value objects, entities, repositories, services, controllers -- follow the examples precisely
- Error handling -- follow `references/error-handling-examples.md`
- Tests -- follow `references/test-examples.md`

Do NOT deviate from established patterns. If unsure, read the reference files again.

### Step 3: Code Review Before Commit

After implementation is complete, launch the **code-reviewer** agent to review ALL changes before committing. The code reviewer will check:
- Correctness, security, performance
- Adherence to all Coding Guidelines in this file
- Proper use of project patterns (naming, structure, error handling)

Do NOT commit code that has not been reviewed by the code-reviewer agent. Fix all CRITICAL and HIGH findings before committing.

### Step 4: Verify Formatting & Linting

After writing or modifying ANY file, ALWAYS run lint + format checks before considering the task done:
- **Backend:** `mvn spotless:apply` (auto-formats Java)
- **Frontend:** `npm run lint` AND `npm run prettier` (or combined: `mvn -f basisprojekt-client/pom.xml -P prettier-eslint-fix generate-sources`)
- Vitest/JUnit only run tests -- they do NOT catch lint or formatting errors
- CI will reject code that passes tests but fails lint/format checks

### Summary

```
1. architect agent   -->  produces implementation plan
2. code-patterns skill  -->  follow templates during implementation
3. lint + format       -->  run lint and prettier/spotless on ALL changed files
4. code-reviewer agent  -->  review all changes before commit
```
